# 共享记忆模块设计说明

> 版本：v0.11.2 | 2026-05-28
>
> 涵盖：MemoryUnit 数据模型、MemoryStore 存储引擎、语义检索、evidence_chain 证据链、意图门控与跨任务复用

---

## 一、设计目标

多 Agent 协作解决研究/分析类任务时，每次从零开始调用 LLM 是浪费的——很多子问题在之前的任务中已经解决过。共享记忆模块的核心目标是：

**把每一次任务执行的经验（计划、检索结果、执行输出、最终摘要）沉淀为可检索、可复用、可追溯的结构化记忆，让后续相似任务能直接复用或增量修改，从而大幅降低 LLM 调用次数和 token 消耗。**

实测效果（full24 基准）：全功能模式相比纯文本基线节省 **68.3% token**，同时保持 **24/24 质量通过**。

---

## 二、整体架构

```
┌─────────────────────────────────────────────────────────┐
│                     Agent 层                              │
│   Planner  │  Retriever  │  Executor  │  Summarizer       │
│     │            │            │             │             │
│     └────────────┴─────┬──────┴─────────────┘             │
│                        │                                  │
│              query_memory() 统一入口                       │
│                        │                                  │
│     ┌──────────────────┼──────────────────┐              │
│     │                  ▼                  │              │
│     │         MemoryStore 引擎             │              │
│     │   ┌──────────┐  ┌──────────────┐   │              │
│     │   │  SQLite   │  │ FAISS Index  │   │              │
│     │   │ (元数据)   │  │  (向量检索)   │   │              │
│     │   └──────────┘  └──────────────┘   │              │
│     │                  │                  │              │
│     │   关键词检索  │  标签检索  │ 语义检索  │              │
│     └──────────────────┼──────────────────┘              │
│                        │                                  │
│              意图门控 (task_intent.py)                     │
│         对比 / 合规 / 漏洞 / 审查 / 分析 / 通用              │
└─────────────────────────────────────────────────────────┘
```

三层设计：

| 层 | 组件 | 职责 |
|----|------|------|
| **数据模型** | `MemoryUnit` | 定义一条记忆包含哪些字段、如何序列化 |
| **存储引擎** | `MemoryStore` | SQLite 存结构化元数据 + FAISS 存语义向量索引 |
| **安全约束** | `task_intent.py` | 防止跨意图类型错误复用（如把风能分析模板套到合规审查题上） |

## 三、MemoryUnit — 记忆单元

### 3.1 字段说明

每条记忆是一个 `MemoryUnit` 实例，存储在 SQLite 中。核心字段如下：

| 字段 | 类型 | 说明 |
|------|------|------|
| `memory_id` | UUID | 全局唯一标识 |
| `source_agent` | str | 来源 Agent（planner / retriever / executor / summarizer） |
| `created_at` | float | 创建时间戳 |
| `task_topic` | str | 任务主题描述 |
| `task_id` | str | 关联的任务 ID |
| `summary` | str | 简短摘要（≤200 字符），用于列表展示 |
| `content` | str | 正文（JSON 格式），存储计划、检索结果、执行输出或摘要全文 |
| `tags` | List[str] | 标签列表，如 `["energy", "solar", "comparison"]` |
| `evidence_chain` | List[str] | 证据链：指向支撑此记忆的其他 `memory_id` 列表 |
| `embedding` | List[float] | 384 维语义向量（BGE-small），用于相似度检索 |
| `access_count` | int | 被访问次数，用于热度排序 |
| `last_accessed` | float | 最后访问时间 |
| `confidence` | float | 置信度（0–1），目前默认 1.0 |
| `memory_type` | str | 记忆类型（见下方枚举） |
| `abstraction_level` | int | 抽象层级：0=具体实例 / 1=领域模板 / 2=通用原则 |
| `fill_attempts` | int | SafeSieve-lite：此模板被尝试填充的次数 |
| `fill_successes` | int | 填充成功的次数（生成质量通过） |

### 3.2 记忆类型（memory_type）

| 类型 | 含义 | 示例 |
|------|------|------|
| `result` | 最终执行结果 | 一道题的完整答案 |
| `strategy` | 策略/计划模板 | Planner 生成的子任务 DAG |
| `evidence` | 支撑性证据 | Retriever 从知识库检索到的文献摘要 |
| `fact` | 事实性知识 | 某技术参数、统计数字 |
| `error` | 错误记录 | 执行失败的堆栈信息 |

`error` 类型有特殊语义——**不入库复用**（Store 存储，但检索时过滤），防止错误经验被后续任务套用。

### 3.3 抽象层级（abstraction_level）

```
abstraction_level = 0  →  具体实例："2024年光伏LCOE为$24/MWh"（不可跨域推广）
abstraction_level = 1  →  领域模板："能源技术对比分析计划模板"（同域可复用）
abstraction_level = 2  →  通用原则："先检索再执行"（跨域可复用）
```

这个设计使得检索时可以分层匹配：先用通用原则（level=2）兜底，优先命中领域模板（level=1），具体实例（level=0）仅在高度相似时复用。

## 四、MemoryStore — 双引擎存储

### 4.1 SQLite（元数据层）

选 SQLite 的理由：零配置、嵌入式、无网络依赖、支持事务。

存储表 `memories` 包含上述所有字段，其中 `tags` 和 `evidence_chain` 以 JSON 字符串存储，`embedding` 以 BLOB（float32 二进制）存储。建立了以下索引加速查询：

- `task_topic`（主题检索）
- `tags`（标签检索）
- `memory_type`（按类型过滤）
- `abstraction_level`（按抽象层级过滤）

另有 `access_log` 表记录每次访问的 `(memory_id, agent_id, accessed_at, task_id)`，用于分析记忆使用模式。

### 4.2 FAISS（向量索引层）

语义向量使用 `BAAI/bge-small-en-v1.5` 模型，输出 **384 维 float32 向量**。写入时 L2 归一化后存入 `IndexFlatIP`（内积等价于余弦相似度）。

索引升级策略：
- 向量数 < 100,000：使用 `IndexFlatIP`（暴力搜索，O(N)，小数据集足够快）
- 向量数 ≥ 100,000：自动切换到 `IndexHNSWFlat`（图搜索，O(log N)）

### 4.3 去重机制

`store()` 方法在写入前执行语义去重：如果已存在一条同类型记忆且余弦相似度 > 0.95，则不再新建，改为更新已存在记忆的访问计数。这避免了同一知识点被反复存储。

### 4.4 统一检索入口

每个 Agent 通过 `BaseAgent.query_memory()` 访问记忆：

```
query_memory(query, tags, use_embedding=True, limit=5)
         │
         ├─→ search_by_keyword(query)    → SQL LIKE 匹配主题/摘要/内容
         ├─→ search_by_tags(tags)         → 标签 OR 匹配
         └─→ search_by_similarity(embedding) → FAISS Top-K 语义检索
                          │
                    合并去重，按分数排序，记录访问日志
```

三种检索方式**并行执行、结果合并去重**，确保既不漏掉精确关键词匹配，又不漏掉语义相近但用词不同的记忆。

语义检索的排序不是单纯按相似度，而是 **综合效用分数**：

```
utility_score = 0.75 × 余弦相似度 + 0.15 × min(1.0, access_count/10) + 0.10 × 模板成功率
```

这个公式让"被频繁使用且结果好"的记忆排名更靠前，避免只用相似度导致的高分低质问题。

## 五、evidence_chain — 证据链

### 5.1 设计动机

多 Agent 协作时，Summarizer 的最终报告是基于 Planner 的计划、Retriever 的检索结果、Executor 的执行输出综合而成的。如果只存最终结果，丢失了"这个结论是怎么来的"这一推导过程。

### 5.2 数据结构

`evidence_chain` 是一个 `List[str]`，存储指向支撑记忆的 `memory_id` 列表：

```
                    ┌─────────────────────┐
                    │  Summarizer 摘要     │
                    │  memory_id = m4      │
                    │  evidence_chain =    │
                    │    [m1, m2, m3]      │
                    └─────────┬───────────┘
                              │
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
      ┌──────────┐    ┌──────────┐    ┌──────────┐
      │ Plan m1  │    │ Retrieve │    │ Execute  │
      │ (Planner)│    │   m2     │    │   m3     │
      └──────────┘    └──────────┘    └──────────┘
```

### 5.3 使用场景

| 场景 | 利用方式 |
|------|----------|
| **根因追溯** | 沿着 `evidence_chain` 回溯，找出结论是依据哪条检索结果得出的 |
| **可信度评估** | 如果某条证据记忆被标记为 `error` 或低 `confidence`，其下游记忆自动降权 |
| **增量更新** | 当知识库某条信息变更时，沿证据链找出所有受影响的记忆并标记为待刷新 |
| **跨任务关联** | 两条记忆共享相同的 evidence 节点 → 它们解决的是同类问题，可以聚类为模板 |

### 5.4 当前实现程度

evidence_chain 的数据结构和读写 API 已完备。当前在 Agent 执行流程中自动记录——Planner/Retriever/Executor 的记忆 ID 被聚合到 Summarizer 的记忆中。深度推理（如自动根因分析）属于后续增强方向（见路线图 P1-8）。

## 六、意图门控 — 防止跨意图错误复用

### 6.1 问题场景

系统在热记忆状态下运行：先做了一组"风能 vs 光伏对比"题（`TaskIntent.COMPARE`），再做一道"SOC2 合规审查"题。如果仅靠语义相似度，合规审查题可能匹配到风能分析的 Summarizer 缓存——因为两者都涉及"逐条分析"这个形式，向量相似度可能不低。但套用缓存会导致合规审查输出风能领域内容（v0.10 中 e4 相关度仅 0.667 的根因）。

### 6.2 意图分类

`task_intent.py` 通过关键词匹配将任务分为 7 类：

| 意图类型 | 触发关键词示例 |
|----------|---------------|
| `COMPARE` | compare, versus, vs, trade-off, contrast |
| `POLICY` | policy only, regulatory only |
| `COMPLIANCE` | soc2, iso27001, compliance framework |
| `VULNERABILITY` | sql injection, command injection, path traversal |
| `REVIEW` | code review, audit, vulnerability assessment |
| `ANALYZE` | analyze, research, explain, describe |
| `GENERAL` | 默认，不匹配以上任何类型时 |

其中 **严格意图**（`_STRICT_INTENTS`）包括 `COMPARE`、`POLICY`、`COMPLIANCE`、`VULNERABILITY`——这些类型的缓存**只能同类型复用**，不允许跨意图。

### 6.3 门控位置

意图门控在三个缓存点生效：

```
任务到达
    │
    ▼
┌─────────────────────────────────────┐
│ 1. E2E 整题复用 (_try_e2e_reuse)     │
│    ├─ requires_fresh_synthesis()?    │  ← COMPARE/COMPLIANCE/REVIEW 必须新建
│    └─ cache_intents_compatible()?    │  ← 严格意图只能同类型
├─────────────────────────────────────┤
│ 2. 领域计划注入 (_load_domain_plan_hint)│
│    └─ cache_intents_compatible()?    │  ← 同样检查意图兼容
├─────────────────────────────────────┤
│ 3. Summarizer 缓存                    │
│    └─ 摘要 E2E 门控 (cos ≥ 0.72)     │  ← 额外嵌入相关度门槛
└─────────────────────────────────────┘
```

### 6.4 补充防护

- **tags 标签匹配**：不同标签的任务不会跨域复用（如 `["energy"]` 的缓存不会命中 `["security"]` 的查询）
- **摘要嵌入相关度 ≥ 0.72**：Summarizer 的 E2E 不仅检查意图兼容，还需要摘要与当前任务的嵌入相似度达标
- **对抗集验证**：full24 中有 6 道故意设陷阱的对抗题（看起来像旧题但要求不同），当前版本 **0/6 误用旧答案**

## 七、跨任务复用机制（三级缓存）

```
相似度高 (cos ≥ 0.85)
  ┌── E2E 整题复用：整份答案直接返回，几乎 0 token ──────────────┐
  │   条件：同标签 + 意图兼容 + 嵌入相似度 ≥ 0.85                  │
  │                                                              │
相似度中 (cos 0.68–0.85)                                        │
  ├── Summarizer E2E：复用摘要结构，LLM 微调差异                    │
  │   条件：同标签 + 意图兼容 + 嵌入相似度 ≥ 0.72                   │
  │                                                              │
  ├── 领域计划注入：复用 Planner 的子任务 DAG 模板                  │
  │   条件：同标签 + 意图兼容 + 策略嵌入相似度 ≥ 0.68               │
  │                                                              │
相似度低 (cos < 0.68)                                            │
  └── 从零执行：全部 Agent 重新跑                                  │
```

### 7.1 E2E 整题复用

最高效的复用方式。当一道新题与某条历史记忆的语义相似度 ≥ 0.85，且通过意图门控和标签检查，直接返回历史结果。对于这种命中，LLM 调用次数为 0。

### 7.2 领域计划注入（Domain Plan Hint）

当语义相似度在 0.68–0.85 之间时，不足以整题复用，但足够复用 Planner 的子任务分解结构。系统从 MemoryStore 检索 `memory_type="strategy"` 且 `abstraction_level ≥ 1` 的记忆，将其中的 `subtasks` 结构注入 Planner 的系统提示，让 Planner 在已有模板基础上"只改差异部分"，而非从零生成计划。

### 7.3 模板只填差异（Template Filling）

Planner 拿到领域模板后，LLM 被指示只修改 `query` 和 `context` 等差异字段，不重写整个计划 JSON。这大幅缩短了 completion 长度（`max_tokens=256`），节省 token。

### 7.4 Executor Dropout

对于不需要代码执行的分析类题目，直接跳过 Executor Agent。系统判断依据：
- 任务的嵌入向量与需要执行的题型的向量距离较远（阈值 0.65）
- 意图类型不是 `REVIEW` 或 `COMPLIANCE`（这两类需要专门的执行通道）
- 在 full24 中，约一半的题跳过了 Executor

## 八、SafeSieve-lite — 模板质量反馈

### 8.1 设计动机

模板复用有风险：如果某条策略记忆的模板填充后屡次产出低质量结果，继续复用它就是在传播错误。

### 8.2 机制

`MemoryUnit` 中有两个计数器：

```
fill_attempts   → 该模板被填充的总次数
fill_successes  → 填充后产出合格结果的次数
```

每次 Summarizer 生成结果并通过质量检查后，调用 `record_template_outcome(memory_id, success=True/False)` 更新计数。

### 8.3 分数惩罚

在语义检索排序时，`effective_similarity()` 会检查模板历史成功率：

```python
def effective_similarity(mem, raw_score):
    rate = fill_successes / fill_attempts
    if fill_attempts >= 2 and rate < 0.25:
        return raw_score * 0.45      # 严重降权
    return raw_score * (0.65 + 0.35 * rate)  # 按成功率平滑调整
```

连续失败 2 次以上且成功率低于 25% 的模板，相似度分数被砍半以上，在排序中会被挤到后面，自然被淘汰。

## 九、与 Agent 执行流程的集成

```
Orchestrator.execute_task(task_description, tags)
│
├─ 1. 意图识别：detect_intent(task_description, tags)
│      → 决定缓存策略（严格意图禁 E2E、禁 Dropout 等）
│
├─ 2. E2E 检查：_try_e2e_reuse(task_description, tags)
│      → 语义检索 → 意图门控 → 标签匹配 → 相似度判断
│      → 命中则直接返回，跳过剩余步骤
│
├─ 3. 领域计划注入：_load_domain_plan_hint(task_description, tags)
│      → 检索 strategy 类型记忆 → 意图兼容 → 注入 Planner 提示
│
├─ 4. Planner 执行：生成子任务 DAG
│      → 计划写入 MemoryStore (memory_type="strategy", abstraction_level=1)
│
├─ 5. 并行执行：Retriever + Executor
│      → 各自 query_memory() 查历史
│      → 结果写入 MemoryStore
│
├─ 6. Summarizer 执行：综合计划 + 检索 + 执行结果
│      → 检查摘要缓存（嵌入相关度 ≥ 0.72）
│      → 生成最终报告，evidence_chain 指向步骤 4–5 的记忆
│
├─ 7. 质量验证 + 模板反馈
│      → 质量通过 → record_template_outcome(plan_mem_id, success=True)
│      → 质量失败 → record_template_outcome(plan_mem_id, success=False)
│
└─ 8. 指标采集：消息数、token、记忆命中率、墙钟时间
```

## 十、关键阈值汇总

| 阈值 | 默认值 | 作用 |
|------|--------|------|
| E2E 整题复用 | cos ≥ 0.85 | 整题结果直接返回 |
| Summarizer E2E | cos ≥ 0.72 | 摘要结构复用 + LLM 微调 |
| 领域计划注入 | cos ≥ 0.68 | Planner 模板填空 |
| Executor Dropout | cos ≤ 0.65 | 跳过不需要代码执行的题 |
| 语义去重 | cos > 0.95 | 相同知识不重复存储 |
| 严格意图 | COMPARE/POLICY/COMPLIANCE/VULN | 仅同类型复用，禁止跨意图 |
| SafeSieve 降权 | 成功率 < 25% | 相似度分数 × 0.45 |

## 十一、局限性

| 维度 | 当前状态 | 改进方向 |
|------|----------|----------|
| **嵌入模型** | bge-small（384 维） | 换 bge-base 可提升相似度区分力，预计 E2E 命中 +1–2 次 |
| **证据链推理** | 结构已完备，被动记录 | 可做主动根因回溯、跨链关联聚类 |
| **事实性** | 依赖内置模拟知识库 | 接真实 RAG（PDF 上传 / 搜索 API） |
| **时序关系** | 记忆间无时序建模 | 对连续任务链可加入"先于/后于"关系 |
| **模板抽象** | 模板抽象层级由 Planner 生成质量决定 | 可引入自动聚类，将多个 level=0 实例归纳为 level=1 模板 |
